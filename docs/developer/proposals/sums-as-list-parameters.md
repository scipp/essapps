# Sums over runs as list parameters

**Status: proposal, implemented in the skeleton on branch `4-sums-as-list-parameters`, stacked on `architecture-sketch`.**
It replaces the aggregation part of [run-records.md](run-records.md).
The topic docs ([architecture.md](../architecture.md), [aggregation.md](../aggregation.md), [rules.md](../rules.md), [records.md](../records.md), [stages.md](../stages.md), [workflow-contract.md](../workflow-contract.md)) still describe the design this replaces, and are to be updated once the direction is agreed.

## Summary

- A run request is always a whole configured pipeline: the spec, every parameter value, and the outputs to compute. It never holds a piece of a pipeline.
- A sum over runs is one run request whose run parameter is a list. The workflow code computes the sum, as `sciline.Aggregation` does, inside one run.
- Stages and accumulations are caches. A session holds them, next to the workflow code and its dependency graph.
- As a result, the backend never needs to know the graph. The spec gets no `reads` table, and what a caller varies is a hint given with the submission, not part of the record.

```python
# Before: a member stage per run, a finalize stage, and an Accumulate reference
normalize = Template(spec=NORMALIZE, params={'floor': 1.5, 'scale': 2.0})
member = normalize.cut(blanks=('run',), outputs=('numerator', 'denominator'))
finalize = normalize.cut(blanks=('numerator', 'denominator'), outputs=('normalized',))
members = [client.run(member, {'run': r}) for r in runs]
total = client.run(finalize, {
    name: Accumulate(accumulate=[m.ref(name) for m in members])
    for name in ('numerator', 'denominator')
})

# After: one run over the list of runs
total = client.run(NORMALIZE, {'runs': runs, 'floor': 1.5, 'scale': 2.0})
```

## The problem

In the design this replaces, a sum over runs is recorded in pieces.
Each run has a member record, the stage from the run to the numerator and denominator.
A finalize record is the stage from the accumulated numerator and denominator to I(Q).
The finalize record supplies those intermediates as an `Accumulate` reference to the member records.

Pieces must fit together: the members and the finalize must be pieces of one configured pipeline.
The masks a member used must be the masks the finalize claims.
Checking that requires knowing which parameters each piece reads, and only the workflow code knows the graph.
The spec is the signature of the pipeline, and a signature does not say which argument affects which output.

The backend therefore guessed.
Each guess broke somewhere:

1. **A member of a sum with two run lists is refused.**
   The sample member's request leaves `background_run` unset.
   The backend checks a request that supplies no intermediate against the whole params model, so it refuses the member: `background_run: Field required`.
   The member's stage never reads `background_run`, but the backend cannot tell.
2. **A request cut at an intermediate is validated only when it runs.**
   Which parameters such a request needs is known only to the workflow code.
3. **A value in `params` means one of three things.**
   The run read it; or the cut made it irrelevant; or the run did not read it, but the agreement check guarantees that the member records did.
4. **`vary` is called a hint, but decides correctness.**
   The agreement check skips every parameter that either side varies.
   A finalize that varies `floor` over members made with another `floor` is accepted, and its record names a value that did not produce its inputs.
   A finalize that changes `scale`, which only the finalize reads, is refused unless it varies `scale`.

The fix on the table was to give the backend the graph: a `reads` table on the spec, listing for each output the parameters it reads, generated by the binding and checked against the pipeline.
That works, but it puts a derived property of the code into a document meant to be written by hand and read without code.
It also makes `vary` part of the semantics of a record, when it describes a caching choice.

## The idea: a stage is how, a record is what

sciline already separates the two.
A pipeline with its parameters set says *what* is computed.
A `Stage` and an `Aggregation` say *how*, and give the same result:

```python
pipeline[QBins] = q_bins
pipeline.compute(IofQ)                                             # what

stage = sciline.Stage(pipeline, inputs=[QBins], outputs=[IofQ])    # how: hold what QBins
stage.compute({QBins: q_bins})                                     # cannot change

aggregation = sciline.Aggregation(pipeline, members=[Filename[SampleRun]], ...)
aggregation.compute({i: {Filename[SampleRun]: f} for i, f in enumerate(files)})
```

The design already follows this for tuning.
A session holds a stage cut at the parameters a slider moves.
The record of each call is the record of a plain run with the same values.
The stage contract says that a result through a stage equals the plain result, and the stage never appears in provenance.

The design this replaces made one exception, sums over runs, and recorded the pieces of the plan.
Every symptom above follows from that exception.

What does a record hold for `Aggregation.compute(table)` if it records only the *what*?
It holds the pipeline with the table as a parameter value.
For a sum over runs, that is a parameter holding the list of runs.
ess.sans already has this signature.
It registers `with_sample_runs` as the parameter mapper of `Filename[SampleRun]`, and `ess.reduce.workflow` applies it when a parameter widget holds a list of files: the reduction is mapped over the files and merged at the numerator and denominator.

This splits the work cleanly between records and caches:

| | knows the graph | durable | may be dropped |
|---|---|---|---|
| run record | no | yes | no |
| held stage, held accumulation | yes | no | yes |

Knowledge of the graph is needed only to decide what can be held and reused.
It lives in the binding, next to the pipeline.
A mistake there can make a held stage return a wrong result, but the request still says exactly what was asked, and publication recomputes any result a held stage served.

## What it looks like

### A sum

```python
runs = [dataset_ref(instrument='dream', run=n) for n in (1, 2, 3)]
total = client.run(NORMALIZE, {'runs': runs, 'floor': 1.5, 'scale': 2.0})
total.request.params['runs']        # the three runs: the record names what it sums
```

The spec says the sum is part of the signature:

```python
class NormalizeParams(BaseModel):
    runs: list[OpaqueFile] = Field(min_length=1)
    floor: float = 0.0
    scale: float = 1.0
```

The backend validates the request against the whole params model, like any other.
An empty list is refused at submit, because the params model says so.

### Two lists

```python
client.run(BACKGROUND, {'sample_runs': samples, 'background_runs': backgrounds})
```

This is a plain run.
User story S6, refused before, passes.

### Adding a run, removing a run

A template whose blank is the list names the stage a session holds:

```python
total = Template(spec=NORMALIZE, blanks=('runs',), name='sum')
first = client.run(total, {'runs': [r611, r612]})
added = client.run(total, {'runs': [r611, r612, r613]})    # contributes only r613
removed = client.run(total, {'runs': [r611, r613]})        # accumulates both again
```

The held stage keeps the accumulation over the runs it has seen.
A call whose list begins with those runs contributes only the rest.
Any other list starts a fresh accumulation, and nothing is ever subtracted.
Each record names every run it sums, and recomputing it needs nothing from the session.
This is the rule the session previously applied to held accumulators, moved into the stage the binding builds.

### Tuning a parameter over a sum

```python
tune = Template(spec=NORMALIZE, params={'runs': runs, 'floor': 1.5}, blanks=('scale',))
client.run(tune, {'scale': 2.0})     # normalisation reads scale: the sum is reused
tune = Template(spec=NORMALIZE, params={'runs': runs, 'scale': 2.0}, blanks=('floor',))
client.run(tune, {'floor': 0.0})     # each run's numerator reads floor: accumulated again
```

The binding decides which of the two applies, from the graph.
The caller only says what varies.

### What varies is not recorded

Where a session cuts the pipeline does not change the result, so the record does not say.
The names a caller varies travel with the submission, not with the request:

```python
client.run(tune, {'scale': 2.0})                 # submitted with tune.blanks
client.submit(request, vary=('scale',))          # the same, by hand
group = apply(client, rule, datasets)            # a Group: the requests, and
group.vary                                       # the rule template's blanks
client.submit_group(group)                       # submitted with group.vary
```

A plain mapping of requests submits with nothing varied.

The record of a call through a held stage equals the record of a plain run with the same values.
Whether a held stage served it is in `reused`, which publication checks.
The backend keeps the names in memory from submission to dispatch.
A record dispatched after a restart runs without them: it holds nothing and gives the same result.
The session names a held stage by the spec, the values not varied, the names varied, and the outputs.
No workflow ID exists outside the session.

### A series under a rule

```python
rule = Rule(
    name='sans-series',
    template=Template(name='sans-defaults', spec=NORMALIZE.id,
                      params={'floor': 1.5}, blanks=('runs',)),
    selector=Selector(match={'role': Like(pattern='sample')}),
    series=Series(key='sample'),
)
```

On each arrival the rule submits one request.
Its dataset field lists every current run of the series: the datasets with the same value of `sample` that the selector matches and that are not excluded.
The series value is the member key, so successive requests supersede each other, and the batch table has one row per sample.
A run that arrives again, or out of order, is listed once.

`Series` needs only its key.
A sum and a stitch look the same to the rule, because what the workflow does with the list is the workflow's business.
This settles the open question of a rule over a stitch: reflectometry's angle series needs a spec over a list of runs, which `ess.apps.amor` does not have yet.

Two consequences:

- **A run that cannot be read fails the whole series request, visibly.**
  Before, a failed member was silently left out of the next finalize.
  Now the operator excludes the run, and `retry` submits the series without it.
- **Every run of a series is filled alike.**
  A series is one request, so one value per parameter.
  If a lookup fills a field differently for two runs of one series, `apply` refuses the series and names the runs.
  This is a comparison of values, and needs no graph.

### Supplying a value from outside

A beam centre found in one view and used in the next is a parameter whose value may be a reference to another record's output.
`ess.apps.loki` already binds it that way: `beam_center: Quantity | OutputRef`.
In sciline terms, setting a key replaces its provider, so no separate notion of a supplied intermediate is needed.
If the author wants the finder to run when no value is given, the parameter is optional and the binding sets the key only when a value is present.

### Reducing the runs of a sum on separate nodes

A sum inside one request runs in one process.
To spread the runs over nodes, compose two specs over references, as `SUM` and the amor stitch already do:

```python
# CONTRIBUTE and COMBINE are illustrative: one run to numerator and denominator,
# and a list of numerators and denominators to I(Q).
member = Template(spec=CONTRIBUTE, params={'floor': 1.5}, blanks=('run',))
parts = [client.run(member, {'run': r}) for r in runs]    # independent requests
total = client.run(COMBINE, {
    'numerators': [p.ref('numerator') for p in parts],
    'denominators': [p.ref('denominator') for p in parts],
    'scale': 2.0,
})
```

Each record describes only its own computation.
`COMBINE`'s record says which outputs it combined and with which `scale`, and claims nothing about the masks of the members.
The members are one reference away.

This costs three things compared with one request over a list:

- **The intermediates become outputs.**
  `CONTRIBUTE` must expose the numerator and denominator with a format the store can write, because they leave the run.
- **Nothing checks that the pieces fit.**
  A combine over members reduced with different masks is accepted.
  A parameter read on both sides, such as a wavelength band, is set twice and never compared.
  Making every member from one template, as above, makes them agree by construction.
- **Members in other processes reach the combine through disk.**
  Only in one process can the intermediates stay in memory.

A rule cannot drive this.
`Series` fills a dataset field with the current runs of the series, not a list of references to the records of another rule.

## The binding

A sciline binding names its member parameters and gives an accumulator per accumulation key:

```python
PipelineAdapter(
    normalize_pipeline(),
    keys={'runs': RunFile, 'floor': Floor, 'scale': Scale},
    resolve={'runs': 'path'},
    targets={'normalized': Normalized, 'numerator': Numerator, 'denominator': Denominator},
    members=('runs',),
    accumulators={Numerator: sciline.Buffered(add), Denominator: sciline.Buffered(add)},
)
```

For each member parameter that the requested outputs need, the adapter builds a contribute stage.
It goes from the member key, plus any varied parameter the contributions read, to the accumulation keys that depend on the member.
One finalize stage goes from all accumulation keys, plus the varied parameters read after them, to the outputs.
This is `sciline.Aggregation`, with the extra stage inputs that tuning needs.
The adapter finds "which varied parameters the contributions read" with `sciline.Stage(...).keys`.
That is the `reads` table, computed where the graph is, when a stage is built.

An output that needs each run separately, and not only what the runs accumulate to, is refused when the stage is built.
An example is the counts of one run in a sum.

The accumulation keys need not be exposed in the spec.
`BACKGROUND` exposes none.
They never leave the run, so they need no format, and anything the accumulator can combine works, such as essreflectometry's lists of ORSO entries.
`intermediates` remains, meaning only outputs that a plain run does not compute and a request may name, such as a detector image.
Over a sum, such an output is its accumulated value.

The workflow contract gets smaller:

```python
class Workflow(Protocol):
    def stage(self, params: BaseModel, inputs: Collection[str],
              outputs: Collection[str], data: Inputs) -> StageCall: ...

class StageCall(Protocol):
    def __call__(self, params: BaseModel, inputs: Inputs) -> Mapping[str, Any]: ...
```

`Workflow.accumulator` and the intermediates argument of a stage call are gone.

## What changes

Gone:

- `RunRequest.supplied`, `Accumulate`, and the resolution of both in the runner;
- the agreement check between a supplied intermediate and the request consuming it;
- member and finalize requests of a series, `_finalize`, `_current_members`, and `Series.accumulate` and `Series.outputs`;
- held accumulators in the session store (`Stages.accumulate`): a stage over a list holds its own accumulation;
- field-by-field validation of requests that supply an intermediate: every request is checked against the whole params model;
- `vary` as input to any check: `Template.from_request` keeps a varied value, so a saved template keeps what was tuned (user story B1 passes);
- `RunRequest.vary`, `RunRequest.fixed`, and the workflow ID, with its column in the record store.

Unchanged:

- references, datasets, groups, and pending outputs as the one scheduling primitive;
- records complete without the session;
- labels, member keys, superseding, templates, lookups, rules, and the trigger loop, apart from series;
- combinations over references to other records' outputs, such as `SUM` over a list of `OutputRef`;
- the framework never adds arrays and never imports sciline.

New:

- `PipelineAdapter(members=...)`;
- `vary` on `Backend.submit` and `Client.submit`, and `Group`, the requests `apply` makes with the template's blanks, which `Client.submit_group` passes on;
- a session keeps the checksum each dataset had when it read it, and drops every held stage when a dataset's bytes change.
  A held stage knows the runs of a sum by identity, and a run acquired again keeps its identity.
  This replaces the checksums in the name of a held stage.

In the skeleton, the source is about 150 lines shorter.
All 249 tests pass, and the stories S6 and B1 move from expected failures to passes.

## Costs

- **The runs of one request over a list do not reduce in parallel across processes.**
  Inside one run, the scheduler of the stages can still run them in parallel.
  Across processes, a client composes two specs over references ([above](#reducing-the-runs-of-a-sum-on-separate-nodes)), with its intermediates as outputs and no check that the pieces fit.
  A rule cannot do that composition.
  No user story needs one sum spread over several nodes: the large-batch stories (D1, D2) are independent runs, which stay one request each.
- **A series under a rule, without a session, reduces all k runs on the k-th arrival.**
  With member records, the k-th finalize read k stored contributions.
  A disk cache of contributions would restore that.
  The binding knows the exact key, the values the contribute stage reads plus the run's identity and checksum, and the cache would be invisible in the records.
  It is not built.
- **One bad run fails the series request until someone excludes it.**
- **A request for an intermediate output must set every required parameter**, including those the output does not need.
  An author who wants otherwise makes the parameter optional.
- **A changed dataset empties the session's whole store**, not only the stages that read it.
  Datasets change rarely, and the rule is simple.
- **`sciline.Buffered` still holds every contribution in memory**, as before.
- **A group assembled by hand varies nothing**, so its members share no held stage.
  A form that picks requests one by one calls `apply` once over all of them instead, as `loki-batch-ui.ipynb` does.

## Upstream

- **ess.reduce.spec:** nothing beyond `intermediates`, and no `reads`. A list of runs is a plain `list[NexusFile]` field.
- **sciline:** the adapter builds the contribute and finalize stages itself, because `Aggregation` takes no extra stage inputs and one member list at a time.
  `Aggregation` with extra inputs on both stages (the `finalize_inputs=` idea, and its contribute counterpart) would let the adapter use it directly.
- **ess.sans:** the binding would name `sample_run` and `background_run` as member parameters, with accumulators for `NormalizedQ[..., Numerator]` and its siblings, which `_set_runs` merges today.
  The LoKI pixel masks in `ess.apps.loki` have the same shape: `with_pixel_mask_filenames` merges one result per mask file.
  So a member parameter with a merging accumulator should cover them too, though this has not been tried.

## Open questions

1. Is there a real case of a sum under a rule whose runs must be reduced on separate nodes? Interactively, composing two specs covers it.
2. Do scientists want a sum with one unreadable run to fail visibly, rather than be summed without it?
3. When is the disk cache of contributions needed? A measurement of a real SANS series under a rule would tell.
4. Once agreed: update the topic docs, and delete this proposal together with [run-records.md](run-records.md).
