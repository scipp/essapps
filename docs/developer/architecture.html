Architecture sketch

ESS data-reduction applications

The decisions reached so far, why they were made, and what they cost. Nothing here is implemented. The wording is canonical in docs/developer/architecture.md; this page follows it and adds the pictures the prose makes you assemble in your head.

Companion to scoping.mdSpec assumed: scipp/ess#690Branch architecture-sketch

The picture in one paragraph

A user, a script, or an automatic trigger submits a run request: which workflow, with which parameters, on which input data. The backend checks it, writes it down as a run record, and asks a launcher to start a runner: in the same process, in a subprocess, or on the cluster. The runner fetches inputs, calls the workflow, and stores results. Any result, a single number or a large array, can be an input of the next request; large results live in the data store and are named by handles. Interactive work happens in a session: a long-lived process that keeps the workflow and its data in memory between runs, while the records look the same as for any other run. Everything the backend knows is in the records, so any result can be traced back to raw data and recomputed if it was thrown away. Batch reduction is many requests from one template; automatic reduction is a loop that makes requests whenever new data appears. Publishing to SciCat is a separate, deliberate step.

The three ideas the rest depends on

Push on these first

  • Stateless requests, stateful execution (D1). Every run is a complete, reproducible request and gets a record. Execution may happen inside a per-client session that keeps the workflow and its data in memory, and the session never appears in a record. Sessions exist only in local mode initially.
  • One data store with memory tiers (D3). One registry and disk tier owned by the backend, plus a memory tier in every process that holds data: each session, and the shared service. A runner never knows which tier serves it, so whether a run touches disk follows from where it executes.
  • The workflow is a callable (D6). Parameters in, outputs out. A session runner keeps the callable between runs; scipp arrays arrive as objects, so chains stay in memory. A sciline adapter built on StreamProcessor recomputes only downstream of changed parameters and accumulates list inputs.

Two questions to hold the design against while reading: does anything force interactive use through disk, and is "stateless" pinned at the right level? Everything else in this document is either a consequence of these three or independent of them.

Terms

Plain-language definitions. esslivedata uses some of these words differently; the clashes are noted.

Three terms that look alike

  • Handle is a value: the identity of one stored piece of data.
  • Data reference is a field type: a parameter or output declared to hold a handle.
  • Output reference is a second kind of value that any parameter field may hold instead of a literal: "output X of run Y", for data a run has produced or will produce. It exists because small outputs are stored inline and have no handle, and because requests submitted together refer to each other before run IDs exist.
  • Workflow · the scientific code that turns inputs into results. Typically sciline; the framework does not care.
  • Spec · the declared interface of a workflow: name, version, parameters, outputs. scipp/ess#690.
  • Handle · a ticket naming one stored piece of data, without saying where it currently is.
  • Data reference · a parameter or output type whose value is a handle. Such a parameter is an input.
  • Output reference · "output X of run Y", usable as any parameter with a matching type.
  • Run request · everything needed to execute a workflow once.
  • Run record · the request plus what happened: status, outputs, versions. Never "job" (esslivedata clash).
  • Template · a saved, versioned request with blanks. Batch · many runs from one template.
  • Provenance · the chain from any result back to raw data, parameters, and software.
  • Backend · accepts requests, keeps records, owns results. Not esslivedata's Kafka workers.
  • Launcher · decides where a run executes. Runner · the process that executes runs: one and exit, or many in a session.
  • Data store · where data lives. One registry and disk tier owned by the backend, plus a memory tier in every process that holds data. A copy in a memory tier is visible only to its process.
  • Session · a long-lived process of one client that executes runs placed in it and keeps outputs and workflow in memory. A cache over records.
  • Record store · the database of run records.
  • Dataset source · where new datasets are discovered. Trigger loop · watches it and submits runs.
  • Proposal · the experiment allocation that owns data and defines access. SciCat · the catalogue; PID its identifier.
  • Pending output · an output of a run that has not finished, usable as an input already.
  • Local mode · client, backend, launcher, session, data store in one Python process. Shared mode · backend as a service for many people.
  • Warm workflow · the workflow object kept alive in a session, so a rerun recomputes only what changed.

Core model

Six kinds of data, all plain JSON-serializable values even inside one process: spec, handle, run request, run record, template, batch. A request is stateless and complete: sufficient to reproduce its outputs from scratch. Handles appear inside parameter values in data-reference fields, and any field may instead hold an output reference to another request, including a pending one. A record adds run ID, status, timestamps, output values, the resolved parameters including defaults, and the software versions the runner used.

Where data lives

D3. A handle never contains a path. Data in memory lives in exactly one process; there is no shared memory across processes or machines. The data store has one registry and disk tier, and a memory tier in every process that holds data. Where a run executes decides whether its data touches disk.

Sessions

D1. Requests are stateless; execution may be stateful inside a session. Two invariants keep this safe: session identity never appears in a record, and everything a session holds can be recomputed from records. A session is a cache, and losing it costs only time.

Why local-only first

Remote sessions need a memory budget per session, a cap on sessions, idle timeouts, and a store protocol to memory tiers in other processes. Batch and automatic reduction run as a stateless service and the shared web UI submits and inspects, which covers those needs without any of that. A local application is the same web UI hosted in one process next to backend, session, and data cache; the shared deployment is the same UI over HTTP (D14).

Workflow contract

D6. The entry point returns a callable from the validated parameter model to the output model. The only difference between runners is whether the callable is kept between runs. The framework never imports sciline.

Chaining and groups

D13 and D16. One primitive covers map, combine, and chunking: a pending output used as an input. A group of requests is submitted atomically, refers to its members by local alias, and the backend holds a request until its pending inputs are available.

Failure handling

  • Backend restart. Records are durable; queued requests are re-dispatched, running ones reconciled.
  • Cancel of a running request asks the launcher to stop it; dependents are cancelled.
  • Session loss. A closed or crashed session drops its memory tier and its warm workflow. Runs in flight there fail and the client resubmits; anything else is recomputed on demand.
  • Failure surfacing is in scope from the start: a user must see why a run failed without reading logs. Facilities with automatic reduction report the monitoring UI was most of the value.
  • Slow or missing shared filesystem. Fetching inputs has a timeout and a distinct failure status.
  • Multi-tenancy. Proposal access is checked on every handle dereference, not only at submission. Cluster jobs run under the submitting user's account.

Execution modes mapped onto the model

  • ManualSubmit one request, inspect outputs, resubmit with changed parameters.
  • InteractiveManual inside a session (D1), with a warm workflow (D6) driven by plot selections in a slot (D10). Local mode only until remote sessions exist.
  • BatchTemplate plus per-member overrides, independent records (D12).
  • AutomaticTrigger loop plus template (D11).
  • Map, combine, chunkingBatch plus a dependent combine (D13).
  • PublicationExplicit publish of a handle to SciCat (D4).

Decisions

Numbering is stable; add at the end. Each card gives the decision, the reason, and the cost.

D1

Requests are stateless; execution may be stateful inside a session

WhyBatch, automatic reduction, and provenance need complete requests; those are properties of the record, not the process. Interactive work needs sub-second reruns with multi-gigabyte intermediates in memory.

CostTwo lifetimes for the workflow object. Remote sessions need budgets, caps, idle timeouts, and view routing, so they are deferred and the shared web UI has no interactive loop yet.

D2

Incremental recompute by splitting workflows, when the consumer is outside the session

WhySplitting is the only strategy that works on a fire-and-forget remote runner, and shared artefacts like processed vanadium are genuinely separate workflows. Inside a session the warm workflow makes the split unnecessary.

CostThe cut is not always clean (vanadium must be oversampled). Both stages share parameters. The spec does not yet say which parameters are cheap, so the UI cannot pick a slider over a run button.

D3

Handles are opaque and data is tiered; memory never crosses a process

WhyWriting a huge intermediate is wasted work when its consumer is in the same process. A distributed memory layer would work badly with scipp objects and cost a lot. Recompute is often cheaper than storage. Making a session's memory an ordinary tier of the store is what lets a remote session be added later, and letting the store pick memory or disk from the process it runs in means the launcher decides only where a run executes.

CostPlacement is explicit in the launcher interface. Shared mode pays a disk write, a read, and a process start per run. In shared mode the store spans processes, and its registry must know which memory tiers hold a copy.

D4

Only finalized data enters SciCat

WhyData in SciCat cannot be removed through the regular API. Publication is explicit and idempotent; SciCat inputs are handles with the PID as ID, so raw files and our outputs are the same type.

CostA separate step the user or a rule must take.

D5

The record store is ours, small, and implementation-agnostic

WhyWorkflow engines bake the graph into code and give no stateless request a notebook, a trigger loop, and a batch UI can all emit. Resolved values and package versions are what make "recompute from the record" true. Identical requests may reuse outputs.

CostWe own a small scheduler: dependencies, failure propagation, cancellation. Facilities that went this way later added a broker; "no broker" is a local-mode decision.

D6

Framework-to-workflow contract: a callable from parameters to outputs

WhyArrays as objects keep a chain in memory while workflow code looks the same in every mode. One callable rather than a separate incremental protocol keeps one execution path. Reuse inside the adapter is correct by the sciline graph.

CostTwo validation points, the runner's authoritative. Arrays are loaded whole. Accumulation over a list is exact only if nothing else changed; nothing outside the adapter can check that it resets.

D7

One runner, pluggable launch, backend as single writer

WhyOne code path for execution. Single writer avoids the multi-client ownership problems that produced most of esslivedata's hard bugs. No database credentials on compute nodes; short-lived download tokens instead.

CostA startup lock, and every runner report goes through the backend's API.

D8

References resolve at submission, handles materialize at execution

WhyProvenance must not depend on a search that could give a different answer later. Uploaded files have no producing record and no catalogue entry, so they are never evicted.

CostLocal files bound for a remote runner are uploaded first.

D9

Instrument plus proposal scopes everything

WhyIt is the unit users think in and the unit SciCat authorizes by. Instrument-shared artefacts (direct beam, masks, vanadium) are readable from any proposal on that instrument.

CostMandatory fields on every record; comparison across proposals needs membership in both.

D10

Plot selections are ordinary parameters

WhyNo special interactive concept. Each selection change is a stateless run in a client-chosen slot; a new request in a slot cancels queued ones. The slot key is the stable identity a plot needs across superseded runs.

CostSlot runs go to the submitter's session, which initially means local mode only.

D11

The dataset source is abstracted

WhyTwo implementations from day one: SciCat and an in-memory fake. Kafka would couple the backend to streaming infrastructure and reduce uncatalogued data; a request row in a database is the durable desired state esslivedata's command struggle concluded was needed.

CostArrival may be out of order; no monotonic cursor is promised.

D12

Batch members are independent

WhyAnything else is chaining and is expressed with D13. Rerunning a member is a new record with the same batch ID.

CostNone beyond D13.

D13

Map, combine, and chunking use one primitive: pending outputs as inputs

WhyThe smallest addition that covers temperature scans, angle series, mask series, and large-file chunking. Real combines are not sums, so merging cannot be a framework concern.

CostThe small scheduler of D5. Fan-out whose size is only known after reading the file is not covered.

D14

The client interface is the API; HTTP later; notebook first

WhyA UI that reaches into backend internals caused esslivedata's cross-session races. A local application is the same web UI hosted in-process; the shared deployment is the same UI over HTTP. Qt would be a third UI. UI state lives in the record store.

CostA local app in one process shares the interpreter between UI and runs; moving the session to a subprocess needs the remote-session machinery.

D15

Inputs are parameters of data-reference type

WhyEvery difference between an input and a parameter here is behaviour selected by the field's type. Lists of references are allowed; comparing or combining runs is a workflow with such a list as input.

CostThe backend walks a JSON Schema to find reference fields. A small extension to the vocabulary in scipp/ess#690.

D16

Outputs are a typed model in the same vocabulary as parameters

WhyThe spec allows non-array outputs but gives them no type, which breaks "outputs can be inputs" for beam centres and direct beams. With one vocabulary, chaining is a type check between two fields.

CostThe output side of scipp/ess#690 changes shape while the PR is open. Structural validation of arrays happens in the runner.

D17

Views are not runs

WhyExploring a 4D volume by dragging through slices must not create records, and the frontend must never receive the volume. Views are served from the memory tier holding a copy. Overlaying runs is several views; a difference of runs is a workflow.

CostA view vocabulary, and a chunking decision at write time for dense data. Through the interface a user explores declared outputs only; a notebook can compute any sciline node.

Open questions

  • Groups as the automatic-reduction unit. A reflectivity curve needs four angle runs plus a reference; "on new dataset, instantiate template" cannot say "wait until the series is complete".Trigger rules match groups; inputs and overrides are list-valued.
  • Data-dependent fan-out. Grouping events by rotation angle inside one file yields a member list only after a planning step reads the file.A planning run whose output is a list of requests, which the client or trigger loop then submits. Keep it out of the backend.
  • Template sharing. Both stages of a split workflow share most parameters. Facilities that tried inheritance moved to version-controlled read-only templates.No inheritance. A template may be derived by copy; the record keeps the origin.
  • Remote sessions. Where a session runs when interactive use moves to the shared web UI: on the backend host under a shared budget, or as an interactive cluster job with queue latency at session start.Decide once local sessions exist; a cluster job if memory turns out to be the constraint.
  • Name of the backend component. It clashes with esslivedata's "backend services".Keep it unless the two projects are documented together.
  • Memory budget semantics. Who decides to spill, and how a runner reports memory use, including variances.
  • Retention policy for derived data in shared mode.
  • SciCat push mechanism for new datasets, if the deployment offers one.

Deferred, and the next step

Deferred. HTTP transport, real SciCat integration, cluster launcher, the view implementation, spill policy, UI framework, metrics, agent-facing API. Remote sessions: a session launcher, a per-session memory budget and idle timeout, and the store protocol between a session's memory tier and the registry. A hint in the spec for which parameters are cheap to change. Provisional outputs of a running run, for progress display during chunk-wise processing. The memory budget itself is not deferred: every memory tier needs one from the start.

Technology proposals. pydantic for all models; standard-library sqlite3 for the record store, Postgres later; scipp HDF5 for stored scipp data with pluggable serializers for other output types; scitacean for SciCat; FastAPI for the HTTP transport when it comes. No workflow engine, no Dask, no message broker in local mode.

Next step. Review this with the team. Then a spike on D3 and D13, the decisions with the most hidden risk: a memory-tiered data store, an atomic group submit with pending outputs, and a launcher that runs a chain in one session but a fan-out in several processes, exercised by a fake map-combine pair. Testing seams are the fake dataset source and the session launcher. The full walking skeleton, all components in local mode with no HTTP and no UI, follows if the spike holds.
