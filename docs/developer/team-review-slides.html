Part 1 · What is required

Four things users need to do

Manual

Pick data, set parameters, run, look at the result, adjust, run again.

Batch

The same parameters over many datasets, with a few differences per dataset. Watch, cancel, rerun the failures.

Automatic

Every new dataset is reduced without anyone present, and the result lands in the catalogue.

Chain and combine

A beam centre or processed vanadium feeds the next workflow. Angle runs are combined, and the series grows while it is being measured.

Every one of these is the same workflow code started differently, fed differently, and remembered differently.

These four come straight from scoping.md. The fourth was added after the user stories showed how common it is: reflectometry is nothing but angle series, diffraction always has a vanadium stage.

The delivery order the team has in mind

Phase 1shared service, unattended

Automatic reduction

A rule fires on new datasets, a saved configuration is applied, the run executes, the result is published, and a web page shows what fired and what failed.

Done when one instrument's beamtime is reduced end to end against the real SciCat, and an operator sees a failure without reading logs.

Phase 2shared service, a person at a form

Batch reduction

Fill in a form once, apply it to many datasets, watch progress, cancel, rerun failures, save the form for next time.

Done when a two-hundred-member batch can be submitted, monitored, cancelled, and partly rerun from a web page, and its members found by a meaningful key.

Phase 3scope least known

Per-technique applications

Interactive reduction with sub-second feedback, plot selections that become parameters, exploration of large volumes, whatever each technique turns out to need.

Done when we know what each technique needs. We do not yet.

Phases 1 and 2 need no state between runs. Phase 3 is the first place where something must stay in memory between two runs.

This order is from staging.md. Note the reversal: the sketch was written interactive-first because that is where the risk was; delivery is unattended-first because that is where the value is.

Part 1 · What is required

What esslivedata already taught us

Identities that vanish with a process

Jobs were addressed by an identity that died with the worker. Everything else had to compensate. #1042, ADR 0008

So: nothing may depend on a process identity.

Commands over Kafka

Reliable delivery was a long struggle. The conclusion: a request row in a database is the durable desired state that was missing. #856

So: a request is a row before anything runs.

The UI reaching into internals

Fastest way to start, and the source of the cross-session races. #1046, #1098, ADR 0007

So: one API, and the UI only ever uses it.

Jobs stuck as "active"

Acknowledgements were trusted; processes disappeared without one. #823

So: observe liveness, never trust an acknowledgement.

Four choices in the proposal are these four lessons written down.

Part 1 · What is required

What Snakemake learned the hard way

Identity by path, staleness by timestamp

Inherited from Make. Every special case descends from it: ancient(), --touch, --latency-wait, --cleanup-metadata, ambiguous-rule errors, history lost on a rename.

So: a reference names data by identity, never by location. No timestamp, no staleness. You still type a filename; it resolves at submission.

Recording provenance was right; acting on it was not

Version 7.8 began rerunning when parameters, code, or environment changed. Pipelines reran after an upgrade; whitespace edits triggered reruns. An escape hatch shipped within a week. #1677, #1694

So: every record carries resolved values, versions, environment. Recompute is explicit; skipping is the client's visible decision.

An API that was a command line in disguise

One function with the CLI's keyword arguments for a decade. Version 8 rewrote it and moved executors and storage behind plugin interfaces; third-party executors broke.

So: the Python interface is the API. Launcher and data store are narrow seams from the first implementation.

What the scheduler should not do

Data-dependent fan-out went into the scheduler as checkpoints and became the most confusing feature. An optimising scheduler hung until a greedy fallback was added. Outputs are deleted on failure; a log: directive had to be invented so something survives.

So: one primitive. Fan-out with unknown keys is a rule on the completed producer. The runner's log stays with the record.

Four small additions to the proposal came from this: the log on the record, completion by marker alone, batch rerun as a client operation, fan-out as a rule on the producer. The full reading is in snakemake.md.

Snakemake is the engine we are closest to in spirit and rejected in choice 2, so it is worth saying what we take from it anyway. The first card is the big one: most of the sketch's simplicity is that a reference names an identity, a record output or a dataset's PID, and never a path, so nothing goes stale. Say plainly that filenames are still typed: they resolve at submission, and only the identity is stored. The second card is the argument for explicit recompute. The third is D9. The fourth is why the scheduler stays at one primitive.
Part 1 · What is required

What AiiDA learned the hard way

A broker for process control

RabbitMQ became mandatory in 1.0. A RabbitMQ patch release added a 30-minute consumer timeout that killed every longer process; a repair command had to reconcile database and queue. 2.6 made the broker optional, 2.9 shipped a built-in one. #5105

So: the record store is the truth. No broker in local mode; revisit with the cluster launcher.

Checkpointing live workflow state

Long workflows resume after a restart by serialising the process object. Every changelog carries the cost, and the next release cannot continue checkpoints from earlier ones. The FAQ says: restart the daemon after every code change.

So: requests are complete and stateless; a process is a cache. A code change means a new session.

Transient failures pause, they do not fail

Transport tasks retry with backoff, then the process is paused with the cause; verdi process play resumes it from the failed task once the filesystem or key is back.

So: a paused status. A slow mount for an hour must not cost a retry record per run.

What the provenance graph needed beside it

Attributes are immutable because descendants depend on them; extras are a mutable bag for tags and notes. Exit codes declared on the spec made automatic error handling possible. Integer keys did not survive export; UUIDs did.

So: annotations outside provenance, failure reasons declared on the spec, UUID run IDs.

AiiDA proves the record model at millions of nodes over a decade. Its execution model is the opposite of ours and does not transfer. The reading is in aiida.md.

Same shape as the Snakemake slide. The broker story is the second data point after esslivedata's Kafka experience. The checkpoint story is the strongest external argument for D2. The paused state is the one mechanism added on AiiDA's evidence alone.
Part 1 · What is required

What Mantid's ISIS interfaces taught us

Five lookup tables, one shape

Reflectometry's lookup table, per angle within a tolerance; SANS's per-row user file; Powder's cycle mapping by run-number range; FIA's per-instrument specification, which it calls rules; autoreduce's variables per run range. Each: ordered match criteria on dataset metadata, defaults per match, one fallback, edited by the instrument scientist, saved with the batch.

So: the lookup, versioned data beside a template, and our rule, a template with its lookup and a selector for the datasets it applies to. Both are data under D14, shown in part 2. Not a Python callable.

Nobody waits for a series

FIA sums a series again on every arrival; SANS pairs a scatter with its transmission whichever comes last; reflectometry resets the group and stitches again. None waits, because nobody at the instrument can say when the series is complete: the user decides to measure one more angle.

So: a rule with a series key (D14). Key a dataset into a series by metadata; on each arrival the rule submits a combine request, chained to the previous combine when the workflow declares a contribution and over all members when it does not (D14, D15); successive combines of one series supersede each other under the series key.

Staleness by reset, exclusions beside the data

Any settings change resets every row, so one edited lookup entry reprocesses a beamtime without saying which rows it touched. A run excluded from autoprocessing carries a reason and survives re-searches; one merely deleted comes back on the next poll.

So: moving a rule to a new template or lookup version offers the reprocess, a previewed batch over what the old version made, as a second deliberate operation; nothing reruns on its own. An exclusion, with its reason, lives on the rule, and the trigger loop reports it.

The catalogue lagged the file; the batch file is what users keep

Both interfaces read the ISIS journal because the catalogue was "less reliable"; FIA polls a last-run file, and its outputs are unknown to the catalogue. The 4.1 rewrite dropped the script generator as unused; users kept the batch JSON and edited it over a beamtime.

So: SciCat's ingestion lag is a phase 1 question; a filesystem source can only get ahead of the catalogue and wait for the PID. The batch table is a query, the latest record per member under the rule's label, plus the rule's exclusions; not a stored unit.

Mantid is the nearest thing to what we build: batch and automatic reduction used daily at a neutron facility, and in its reflectometry interface they are one thing: a batch tab whose autoprocessing appends rows, which is our rule. Not taken: state reset on a settings change, a free-form options column, script text as the record. The reading is in mantid.md.

Same shape as the two before. The lookup and the rule are the change to the model on Mantid's evidence: the lookup was a callable in the trigger loop, invisible to the web UI and unversioned, and the rule was the loop's configuration. Both are data now, D14, on the slide after the four needs. The second card is why a rule never waits for a series. The fourth card is why there is no stored batch definition: it would copy the records, and the members table is a query. The options column is rejected because forms are generated from the spec, so every parameter is already reachable and an untyped escape hatch would bypass validation. The take line is the ninth pass: the batch tab maps onto the rule one to one, settings to template, lookup table to lookup, autoprocessing search to selector, runs table to the rule's table, so a rule is to a batch what a template is to a request.
Part 2 · The proposal

One idea: every piece of data is "output X of record Y" or a dataset

Two forms of name serve inputs, plots, publication, and provenance. There is no "which run produced this" query, because the name already says it.

This is D1 and the thing to push on. If the team accepts this slide, most of the rest follows. Ask: is there data anyone needs that cannot be named this way? Address the confusion from the first review head on: "no filenames" never meant nobody types one; it means the stored request holds an identity, so a moved or re-archived file cannot make a record stale. Earlier drafts wrapped every file in a "file record" of a built-in spec so that a reference had one form; the tenth pass dropped that. It was a UUID over an identity SciCat already keeps, and nothing it gave, the "which runs used this dataset" query, plotting, the trigger loop, is anything a PID in the request does not give. Nothing is stored per dataset: the proposal check happens at submission, when the PID's SciCat entry is read anyway, and the data store registers a copy only when it makes one, keyed by the same reference. Listing what can be picked is a query over the record store and the dataset sources, SciCat or a folder, not a table of ours.
Part 2 · The proposal

A record is the request plus what happened to it

The requestcomplete, plain JSON
  • which spec, name and version
  • every parameter: literals, and references to outputs of other records
  • instrument, proposal, who submitted

Sufficient to reproduce the outputs from scratch. Never a path, never a memory address, never a process.

What happenedfilled in by the run
  • status, timestamps, a structured failure reason
  • outputs: small values inline, large ones in the data store
  • resolved parameter values, defaults included
  • package versions and the conda environment
  • how the spec was bound to code, and whether a warm workflow was reused
  • one link to the record it derives from: retry, recompute, or copy
  • a label and member key, under which records supersede: a batch name, a rule's name, or a slot; and a submission, how the request was made: the template version, the rule version and lookup entry when a rule filled it, and the values the submitter typed. Explanation, not provenance
  • beside it, annotations a user adds after inspection: mutable, outside provenance, read by nothing in the framework

Immutable once complete. Never deleted one at a time: a proposal's records are dropped together, after an export. A missing copy of an output is reported, never silently recomputed.

Resolved values and versions are what make "recompute from the record" true. Without them a changed default silently changes what a record means. Records are cheap: a row per run.

Part 2 · The proposal

The four needs, in this model

Manual

One request per run. A rerun with a changed value is a new record, linked to the old one.

Batch

A template, a lookup that defaults each member from its metadata, and per-member values typed by hand (next slide), applied to a set of datasets at once. The batch is the records under one label, not a stored unit: each record carries the label and a member key, and the table of what was reduced is a query, the latest record per member key under the label.

Automatic

A rule: selector with a lower bound, template and lookup, optional series key and combine, retry policy, exclusions, active or paused. The trigger loop applies it to each arrival, and its records are a batch under its name: a rule is to a batch what a template is to a request. Never fires on its own output. Never waits for a series.

Chain and combine

A reference may name a pending output. That is the only scheduling primitive: map and combine are one use of it. An additive combine is declared by the workflow and chained, each arrival referencing the previous partial (D15).

Four modes, one kind of request and one kind of record. The scheduler has one kind of dependency.

Part 2 · The proposal

What fills a request: template, lookup, rule

The lookup and the rule are what the instrument scientist edits during a beamtime: which transmission run and Q range go with which angle, and which datasets to reduce. Both are data, so the web UI shows them, a batch file carries them, and a record's submission names the rule version, the entry, and the typed values that filled it. A rule is to a batch what a template is to a request: the batch form and the trigger loop call one apply, and a rule's records are a batch under its name. A rule with a series key combines the series again whenever a run joins it, chained when the workflow declares a contribution, and never waits (D14, D15).

The lookup and the rule are one section of the document, D14, so give this slide a minute. Every ISIS interface has the lookup table under a different name; the sketch had it as a Python callable in the trigger loop, invisible to the UI and unversioned. Three rules: entries are ordered with one wildcard; a dataset matching two entries is a validation error found before anything runs; editing a lookup makes a new version, and reprocessing runs made from the old version is a separate, previewed batch, never automatic. The rule is what the trigger loop applies; its exclusions and its active state are the only mutable state on it. The batch is not a stored unit: the members table is the latest record per member key under the rule's label, and the ISIS batch file is a rendering of it plus the rule's exclusions. The slot and the batch ID are one label field now, so one query supersedes, cancels, and evicts for a slot, a batch, and a rule; a series' combines supersede under the rule's label with the series value as member key. The loop keeps no memory: it fires on a dataset after the rule's bound that has no record under the rule's label, so restart reconciliation falls out. Creating a rule offers the backlog as a previewed batch; moving it offers the reprocess. Phase 1 therefore already has labels, apply, and the batch table; phase 2 adds the form. If someone thinks in pandas: the batch table is a frame indexed by member key, the template is column defaults, the lookup is an as-of join with tolerance, the ladder is combine_first, the series key is a groupby, and latest-per-member is groupby-last; exact for the view, wrong for the store, because the frame is a query over immutable records, not a mutable table. The document has the full mapping under D14. The skeleton does not have this yet.
Part 2 · The proposal

What lives where: stored data, one apply, records

Who defines what, when: developers write template files at deploy; the instrument scientist edits the lookup and the rule during the beamtime; a user saves a form as a template. Everything is versioned by copy except a rule's exclusions and active state. Live versus existing: the bound decides. After it the loop acts on its own; before it, and for anything already reduced, a person asks and previews.

This slide answers three questions the lookup slide leaves open. Where things live: the top row is stored data, the bottom row is records, and the tables people see are queries over the bottom row; nothing is stored twice. Who defines what, when: the top row's small print. The rule is the one thing with mutable state, and only two fields of it, because exclusions and pausing change over a beamtime while everything else changes by copy so that records can name the version that made them. Live versus existing: the dataset axis on the right. The loop's rule is one clause: a candidate after the bound with no record under the label. It has no memory, so a restart, a pause, and a resume all resolve to the same query, and the trigger status is that query for one dataset. The backlog is offered once when the rule is created, the reprocess when the rule moves to a new version, the rerun whenever failures exist; all three are apply over a query result, previewed through validate, and none happens on its own. A hand-submitted member under the rule's label lands in the same table and supersedes the loop's record for that member, which is how a scientist corrects one run without touching the rule. The skeleton has apply only as the batch function and the loop still keeps a seen-set.
Part 2 · The proposal

The moving parts

Everything the backend knows is in the records, so a restart loses nothing, and any client reaches it only through one interface.

Session as a launcher option is the phase 3 part; in phases 1 and 2 the launcher starts a subprocess. Own record store and small scheduler rather than a workflow engine: none of AiiDA, Snakemake, Prefect gives a stateless request a notebook, a trigger loop, and a batch form can all emit. The dataset source has two real implementations, SciCat and a folder for the local application. Part 2 · The proposal

The contract with workflow code: one callable

The same callable in every mode. The only difference between runners is whether the callable is kept.

Rejected: a file-based contract, which forces every chain through disk; and a framework that knows sciline and caches intermediates itself, which is not affordable with event data. Arrays as objects is what keeps the phase 3 options open in every model.
Part 2 · The proposal

Reduction is combination: declare the accumulation points

What the workflows do

ess.sans merges runs at two nodes, the numerator and the denominator of I(Q): events concatenated, the dense part summed, and normalises once after the merge. Reflectometry stitches angles by a global fit, not additive. Bifrost combines angles inside one run.

The declaration

A contribution output at the accumulation points, opaque to the framework. Three stages: contribute, parameters to a contribution; combine, two contributions to one, associative and commutative; finalize, contribution and parameters to the outputs, with the parameters finalize reads declared. The framework never sums and never sees whether it is events or a histogram.

What it buys

One structure for adding a run in a notebook, a rule's growing series, a summed batch, a parallel reduction of five hundred runs, esslivedata's accumulator, and the phase 3 fold. A chain is one read and one write of the partial per arrival, enough for phases 1 and 2. Removal is a fresh combine, never a subtraction.

Authors must put normalisation after the accumulation point; ess.sans does, ess.powder does not yet (D15).

D14 used to say the rule recombines the members' outputs. That is wrong for the first technique it meets: a SANS member's output is I(Q), and I(Q) curves do not add; what adds is the numerator and the denominator before normalisation. The notebook, the rule, and the fold differ only in how often the partial is written as a record: every addition, every arrival, every n arrivals. The fold's records carry the reused flag, so publication recomputes them cold along the chain, and a rule that publishes its combine therefore chains. A combine that is not additive, reflectometry's stitch or a tomographic reconstruction, stays an opaque workflow over the member outputs, recomputed on every arrival; the rule says which of the two it runs.

Part 2 · The proposal

Where state lives: records never, disk always, memory only in a session

Requests are stateless everywhere. Execution may be stateful in a session, and a session's identity never appears in a record.

Rejected: stateful jobs (esslivedata's model), stateless-everywhere for interactive use (disk-bound at seconds per rerun, unless warm runners are keyed by the reference they hold; see the three-models slide), and a shared object store across processes (scipp is not chunk-aware). Part 2 · The proposal

Our store is not a second catalogue

Only finalized data enters SciCat. Once a reference exists, work continues when the catalogue is slow.

Third review pass removed what would have made the store a replica: entries created by discovery with copied metadata and stored mount paths. Nothing is stored per dataset now; the data store registers a copy only when it makes one. In the local application a folder is the dataset source, read when asked. Publication reads a cold disk copy; a result tuned in a session is recomputed cold first.
Part 2 · The proposal

Failures are the product

Completion marker

A runner writes its outputs, then a marker, to disk before exit. The marker alone is trusted: a file a cluster job wrote appears on other hosts late. Finished while the backend was down is completed, not failed.

Liveness

A silent runner is failed after a timeout unless a marker exists. A run that cannot reach its inputs pauses, and the backend dispatches the same record again when the location is back or an operator asks; not a retry, and not failed.

Reconciliation

On restart the backend re-dispatches queued runs and checks running ones against the launcher and the markers.

Retry is a new record

Never a status reset. The runner's log is kept in the record store beside the record, for the failures nobody foresaw. The trigger loop's refusals are as visible as a run's failure.

Facilities that built automatic reduction report that the monitoring UI was most of the value. Phase 1 is unattended, so this is in from day one.

Part 3 · What we build first

Phase 3 is the real open question: where does interactive state live?

Session model (the sketch)

The framework owns the process. Each change is a complete record, hidden behind a slot label. Shared use needs remote sessions the framework launches, times out, and caps.

Checkpoint model

The application reruns in its own memory, as a notebook does. When the user keeps a result, the full parameter set is submitted and runs cold. The framework never sees a session.

Stateless with splits (two rungs)

Rung 1: every change is a fresh process over a stored intermediate. Seconds. Rung 2: warm runners keyed by the reference they hold serve the rerun from memory. Sub-second, additive, and a routing miss is rung 1.

All three keep the same records, spec, and API. Decide when phase 3 is designed, with measurements from the spike; the checkpoint model is the default to beat, and the third is not to be dismissed on its feedback number, because seconds is rung 1 rather than the model.

Rung 2 is the session model with the addressing rule changed: keyed by the reference held, not owned by a client. D2's invariant survives, the fallback on a miss is the ordinary stateless path, and the cost is a placement policy, because the placement that maximises reuse is the one that destroys fan-out. The last row is not a phase 3 row: D15 answers it the same way in every column, so the model chosen for interactive work does not decide how a growing series is combined, and no column can be justified by accumulation. If a series arrives faster than its partial can be read and written, the fold D15 allows is the third model's second rung, and phase 3 then has a keyed warm pool it did not have to pay for. Two things the core must keep so all three stay open: the callable takes objects, not files; any client may turn a reference into an object in its own process. And one word to keep: nothing may require a request to reach a particular process, which still allows a placement hint.

Part 3 · What we build first

What exists, and the next five steps

Exists today

  • The architecture sketch, with rejected alternatives per choice, a glossary, and a decision index. A reading edition with diagrams is published.
  • 38 user stories run against the sketch: getting data in, interactive, chaining, batch, automatic, publication, roles, operations. Every gap found was closed or became an open question.
  • Five review notes: what each phase needs, what all-in stateless would remove and cost, and what the histories of Snakemake, AiiDA, and Mantid's ISIS interfaces say about the sketch.
  • A walking skeleton, ess.apps, local mode: spec vocabulary, records, SQLite store, data store, both execution shapes, group submit with pending outputs, warm sciline wrapper with a warm-equals-cold test helper, templates, batch, trigger loop, publication, fakes. 64 tests.
  • Not in it: real SciCat, HTTP, a UI, a cluster launcher, Tiled, a real instrument workflow, the contribute, combine, and finalize stages, combine requests.

Next, in order

  1. Make the throwaway launcher the default; keep the session launcher as an experiment outside the phase 1 and 2 tests.
  2. Build the real dataset source and publisher against SciCat behind the existing fakes.
  3. Extend the trigger loop to completed-record events, rules as data with series keys and a bound, lookups, one label field in place of slot and batch ID, apply, and a loop that asks the records instead of remembering.
  4. Choose the web framework for the status page; run it in the backend process against the client interface.
  5. Deploy for one instrument. Let phase 2 start from what the operators ask for.

A spike on the throwaway feedback loop in three configurations, cold, a warm process pool, and a runner already holding the intermediate, so the phase 3 decision rests on numbers. It uses a fake workflow with two accumulation points, run one-shot, as a batch with one combine, and as a chained series, with the grouping helper checking that the three agree.

Nothing here is final. The point of the review is to disagree with a choice, not only with its consequences.
