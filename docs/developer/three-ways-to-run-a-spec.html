Three ways to run a spec

A workflow package offers up to two specs of one reduction: a single-run spec, which takes one run of each kind (sample, can), and a multi-run spec, which takes a table of runs of each kind. A notebook runs a spec as a plain request, or through a template the backend keeps: a stage that tunes a parameter, or an accumulator that grows the tables. Symmetries say which of these choices cannot change the outputs. Slides 1 and 2 are the summary. The panels after them are backup.

spec
The signature of a workflow: name, version, params, outputs.
binding
The code behind a spec, e.g. a sciline pipeline wrapped by PipelineBinding.
record
A request as the backend accepted it. It never changes; its outputs are read by name.
template
A spec with some values fixed and the others left open as blanks.
table, row
A param that is a list of flat rows. A row is one run, or runs that belong together.
push
Appends one row to one or more tables of an accumulator.
plain request
A spec with every value given. The backend keeps nothing between plain requests.
stage, accumulator
Templates the backend keeps. A stage's blanks are replaced on each call; an accumulator's tables grow with each push.
state n
An accumulator after its first n pushes. Not a record; a request that reads it makes one.
accumulating binding
A binding that adds each push to a held state of its own. For any other binding, the backend keeps the rows.
held state
What an accumulator keeps between pushes, e.g. a numerator and a denominator. Private to the binding.

order: pushes into different tables commute
  • Multi-run spec: required to combine runs, and the only spec an accumulator can open. Shared fields: bins, beam_centre, direct_beam, the same in both specs (Backup C). Single-run spec: optional. It matches the per-run sciline graph and the first release, which combines no runs.
  • A stage also works on a multi-run spec: tune bins on a fixed sum of runs. It keeps each run's data, as it is before binning, in memory.
  • Stage and accumulator do not combine. bins is a fixed value of an accumulator's template, so changing it means a new accumulator and pushing every run again.

Not symmetric, on purpose

Stage call vs. push

A stage call makes a record. A push makes a state, which shows up only in the record of a request that reads it. A partial sum is not a record, because no request says which values it holds.

Single-run spec × accumulator

An accumulator appends rows, and a single-run spec has no table to append to.

Cost

Arrival keeps outputs, not cost. If the binding does not accumulate, each read repeats the per-run work for every row so far.

Rows within one table

A state's plain request lists them in push order. Whether order matters is the binding's business; for a sum, only through rounding.

A consequence of arrival: StreamProcessor's context keys, rolling windows, and clear() have no counterpart in an accumulator, because each would break it.

Backup B · An accumulator over time

Pushes advance a state; reads pin one; the held state is added to in place

  • Push and open return once logged. The backend adds pushes one at a time, in log order, on its workers.
  • A read pins the state after the pushes logged so far. A request that references a state not yet reached waits for it, as for a pending record.
  • A state is read only if its plain request would be accepted. Whole-table checks run at the read, not at the push.
  • A partial sum is never a record. To keep one, submit a request that copies the state (COPY).

Today a table maps to one sciline key whose value is the list of rows. #40 would run a plain multi-run request through the same StreamProcessor: push every row, compute the outputs once. With one row, that is the single-run computation, which is the one-row symmetry.

The single-run spec returns what the multi-run spec returns

Never partial results of each run, such as a numerator and a denominator, for a later request to sum. That is the per-run spec + sum + finalize split that ADR 0006 rejects. Combining stays inside the multi-run binding.

Two specs give one result two names

A single-run I(Q) from either spec is a record of a different spec, so labels and provenance split by how it was submitted. Declaring the shared fields the same way in both, as on the left, keeps the two from drifting. A helper that derives the multi-run spec from the single-run one can wait until two packages do this.

StreamProcessor ↔ accumulator
  • base workflow, static part → fixed values, computed once at open
  • dynamic_keys → fields of the table rows
  • accumulate(chunks) → push(rows)
  • accumulators → held state, private to the binding
  • finalize() → outputs(), once per state read
  • context_keys, rolling windows, clear() → none, since each breaks arrival

Backup D · Around the grid

What else a full picture needs, and what it can leave out

Needed to read the grid
  • Records and references. Every connection between requests is a reference: record.ref('centre'), dataset(run=611), or acc.ref('iofq'). A reference to a pending record is valid. The backend waits for it.
  • Template is the shared building block: stage, accumulator, batch (apply), and rules all start from one.
  • Drivers. The backend never decides what to submit or push. A notebook, an app, or the TriggerLoop of rules does.
  • Where it runs. local(): values in memory while the client keeps them. The service (designed, not built): every record's outputs written to a file, each accumulator its own job with a declared memory size and deadline. Placement says the results do not differ.
Orthogonal, safe to leave off the slides
  • Datasets and the dataset source (client.datasets, selectors, watch)
  • Labels and members (tentative)
  • Status, failure, cancel, as_completed
  • Lookups, series, rules
  • Provenance and publication
  • Release and lifetimes of values
